# Evidence-based recovery of an existing Compact & Resume

This procedure collects evidence without changing a running session. It does not establish the historical provider failure from a pickup log, readable page turns, a reload acknowledgement, or a `completed` status alone. A displayed eight-character ticket prefix is not the full continuation token.

## Read-only evidence packet

1. Identify the application's actual user-data directory from the existing service configuration/process arguments. Read copies of `state/continuations.json`, `state/bridge-commands.json`, relevant swarm/Goal state, and the source session's `meta.json`, `events.jsonl`, canonical `messages/` shards, legacy `messages.json` if present, `handoffs/`, and referenced overflow assets. Do not launch the application or import its store against production data. Startup and apparently observational bridge routes can mutate durable state, reconcile work or schedule browser actions.
2. Resolve the displayed ticket prefix against `continuations.json`. Require exactly one match; retain its full token privately. Check `sessionId`, `from`, `to`, phase, source/destination checkpoints, native message IDs, pickup custody, timestamps, captured handoff ID and diagnostics. Compare file hashes/stat information before and after collection; retry the read-only collection if files changed. Record the deployed application and extension revisions separately from the repair branch.
3. From the already-open original provider conversation, inspect visible history without Reload, Send, Stop, Retry/regenerate, or starting a second conversation. Verify the exact user marker and full token, native user-message ID, complete assistant text, terminal state and any error/sign-in banner. Opening another tab or changing navigation is a separate action and needs an explicit operational decision; it is not part of this procedure.
4. Compare the recorded user anchor with the provider message. For the recorder interval after that anchor and before the next native question, require exactly one canonical generation, a latest successful `turn_end`, exactly one nonempty final, and complete authored text. Read the overflow asset when `StoredText.truncated` is true; that flag describes recoverable storage overflow. `textIncomplete` instead means the observer lost bytes before storage. Multiple generations/finals, missing native IDs, a changing snapshot or a bounded scan reaching its limit cannot authorize capture.
5. Validate the full brief on an isolated copy against the deployed parser and the repair revision. Keep the raw source bytes and structured rejection reason. Compare its handoff provenance, saved plan, source session identity, Goal objective/switch, prime/worker family and any replacement command/receipt. A valid brief does not by itself prove replacement delivery.

Never publish tokens, conversation IDs, credentials, repository contents or the user's private brief in a public issue/PR. Do not clear browser data, delete sessions, alter ticket JSON, reset checkpoints, or restart services to collect this packet.

## Options after verified findings

| Finding | Safe next decision |
| --- | --- |
| Exact completed response exists in the recorder; ticket is still awaiting summary | The repaired recorder reconciliation can capture the same ticket and queue one replacement. First review an isolated replay, verify no existing replacement receipt/command conflicts, preserve the ledgers and obtain separate authorization for installing/restarting production. No source resend is needed. |
| Response exists on the provider page but is absent/incomplete locally | Preserve its full text and native IDs. Determine whether the updated observer can report it without navigation. An authorized observation/import must retain original identity and provenance; do not treat a pasted brief as a new provider response or blindly change ticket state. |
| Recorder contains multiple answers, an incomplete observation or a rejected brief | Identify the exact provider branch and complete bytes. Keep the ticket fenced. Resolving ambiguity or manually adopting a brief needs a reviewed recovery operation and explicit authorization; the repair intentionally does not pick the newest answer. |
| Provider is still generating or hydration/completeness is uncertain | Wait and collect evidence. Keep the existing document and send checkpoints intact. Pickup exhaustion is an attention condition, not a reason to reload or resubmit. |
| Ticket is provably predispatch and only page readiness failed | Preserve the same ticket. After a separately authorized installation, the repaired readiness path can retry preparation on that token through the existing native send owner. Require an intact predispatch checkpoint; missing DOM evidence cannot establish this case. Never apply this option to uncertain dispatch or a ticket with incompatible legacy `askedAt` evidence. |
| Verified provider error/authentication expiry | Record the exact error and terminal identity. An operator may separately authorize sign-in repair or provider recovery; these actions may affect the session. They do not imply that the original submission was never accepted. |
| User message is missing from one page snapshot | Delivery remains uncertain. Seek provider-native/history evidence or a complete stable observation. Missing DOM alone never grants a resend. |
| Durable replacement dispatch exists, but commit/receipt is missing | Locate the exact replacement by its full resume marker and native IDs; reconcile the existing session/worker ownership. Do not open a fresh replacement or reuse the brief until uncertain destination delivery is resolved. |
| Ticket is missing, corrupt, terminal, or bound to an unexpected session | Preserve all evidence and stop automatic recovery. Reconstruct only from verified ledgers/receipts in an isolated copy and review the proposed operation. A corrupt/missing checkpoint is not fresh-send authority. |

Any future live recovery must name the exact ticket/session, prove A/B identities, reconcile Goal and worker ownership, preserve browser profile/cookies/extensions/credentials/keyring and the development repository's branches/commits/uncommitted changes, and state whether its first action can cause a browser opening or provider submission. Replacing a binary, restarting a backend, importing observations, committing a continuation, or changing authentication is outside this read-only procedure.
